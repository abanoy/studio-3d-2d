# Loading progress: initial source-only candidate

DRAFT FROZEN for recovery while concrete map-light bugs take priority. No parser/test/engine run, no active app integration, no current1084/Git/receipt change. The sources implement a reusable state/UI and a separate unattached-scene preparation candidate; their native-thread resource behavior is UNQUALIFIED. Do not present this as an available app feature.

The audit confirms SourceImport.launch/_process, HasProject.start/_process/HasProjectLoader and SecondaryHelperEditor.launch/_process already prepare through external/background workers. Their result/status files are final-result channels, not real progress measurements. They currently show text-only windows/labels. Direct App.load_scene/install_project_data, Renderer.prepare_model/prepare_legacy and WorldRuntime.prepare still invoke synchronous SceneIO.load_glb on the main thread. Placing an animated bar around those unchanged calls would freeze repaint and cannot satisfy the request.

loading_progress_state.gd defines has_loading_progress_1: exact operation token, monotonic sequence, bounded phase/label, completed/total/unit. Real known totals admit bytes/items/steps only; unknown totals stay null/indeterminate. No guessed whole-operation percentage, progress interpolation or invented timer. The state rejects stale callbacks, changed denominators, regression, repeated closed phases and token reuse. Cancel stays busy until the existing operation owner acknowledges completion; late success remains cancelled. It grants no authority to install a model/project.

loading_progress_ui.gd creates a shared Window/ProgressBar using current app.theme plus StudioTheme.surface, so Neon and Classic keep existing styling. It shows phase-local real counts without percentage and uses indeterminate mode otherwise. Close delegates exactly one cooperative Cancel to the existing owner. Missing owner/finish releases the view; original workers/cancel/source/revision guards remain authoritative. UI creation must happen before any expensive capture/catalogue step; callers yield one process_frame if doing subsequent main-thread work.

loading_asset_job.gd reads actual chunks on one low-priority Thread, reporting bytes truly read against FileAccess length. It verifies the immutable byte snapshot SHA when supplied and hands those bytes to loading_scene_bytes.gd, which preserves the current Scene3D decoder body and all self-contained-resource/extension checks after file acquisition. GLTF append, scene generation and metadata capture occur on fresh unattached objects only; UI remains on the main thread. No partial scene is installed or exposed before joining. Cancel is checked between read chunks and again at handoff; during uninterruptible GLTF work the UI honestly says cancellation waits for the current step. finish/dispose must run on the main-thread owner and free a rejected staged scene there. Root MUST qualify Godot4.6 off-thread GLTF/texture/metadata creation before any production use. Current source remains unchanged; there is no claim that merely moving arbitrary existing install code into a thread is safe.

Concrete future integration: add optional separate progress-file argument to prepare_source/prepare_generic/prepare_mmd/prepare_vrm/has_project/secondary_helper_worker; emit real phase events through an atomic bounded writer to an owned per-operation progress file. No worker progress writer or worker splice has been implemented in this initial draft. Source worker phases should distinguish dependency discovery (unknown), known bytes/files during copy, conversion (unknown) and verification (known only where totals exist). HAS phases distinguish unpack/copy, real existing snapshot/load worker phases, then main-thread installation. The local-blow worker sequence exposes catalogue/proposal/derive/source-check/basis-check; each result boundary can supply an honest completed step count only after that step finishes, while the current expensive worker phase stays indeterminate.

A fresh caller must open the UI first, retain a unique operation token and revision/source context, stage/observe preparation, await/join all work, revalidate existing source/hash/cancel/revision guards, then run the existing small main-thread installation transaction. Renderer APIs need a separate already-prepared-scene path so they do not reread/decode the GLB. Project loading should prepare each actual asset outside the active tree and count its completed assets when total is known. No current prepare/install call is changed here, and no bar claims overall completion while installation is pending.

loading_progress_unit.gd contains33 authored/unrun state/parser-boundary controls: unknown and real bytes, strict counts/order, stale/new operations, cancel/failure/late completion, and unchanged128MiB asset cap. They do not execute a GLB, prove resource-thread safety, UI repaint, cancellation during a real decode, or worker integration. Root qualifications must include parser, Neon/Classic actual repaint with a large self-contained model, real project/multi-asset loading, local blow preparation, repeated Cancel/close, stale result, failure and current-project preservation. Preserve every existing import/cancel/timeout/Source/height-review control.
