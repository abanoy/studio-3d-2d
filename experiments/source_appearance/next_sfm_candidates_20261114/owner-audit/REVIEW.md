A concrete session-lifetime ownership defect is present in SourceImport normal completion, including cancellation completion. This does not invalidate the25 native app cases or their private Job/desktop closure: those measured workflow/process exit, while the defect concerns retained resources inside a still-running Studio process. No runtime or WinAPI probe was run for this review.

Pinned engine evidence: create_process inserts ProcessInfo at1485-1487. is_process_running at1517-1540 and get_process_exit_code at1542-1565 cache completion without releasing the map entry. The mapped kill branch at1491-1510 removes the entry and closes both handles even when termination of an already-exited process returns failure. These are the [official exact89cea… Windows source lines](https://github.com/godotengine/godot/blob/89cea143987d564363e15d207438530651d943ac/platform/windows/os_windows.cpp#L1449-L1566).

SourceImport._spawn_preparation invokes OS.create_process. Its _process observes completion, immediately assigns pid=-1 and proceeds with status/adoption; it never consumes that owned map entry. Each ordinary successful preparation therefore loses the component's reference needed to release the retained process/thread handle pair. cancel() writes the cooperative cancel file, then follows the same completion path. The scope includes Source, generic, MMD and VRM preparations routed through this component. Successful child exit and successful actor/history/render transport remain compatible with this finding.

Normal user window-close behavior is cooperative: app.gd:2244-2246 calls SourceImport.cancel and requires closing again once pid stops. Source preparation observes its cancel file and terminates/waits for its Blender child in finally (prepare_source.py:202-213). Thus ordinary close does not immediately discard a live preparer. SourceImport has no _exit_tree hook; direct app.quit_studio/tree teardown has no equivalent importer wait guard. This is an uncovered teardown path, not a reproduced ordinary-close orphan. Avoid solving it by unconditionally killing a live Python preparer: forced termination could bypass its Blender-child finally cleanup.

Minimal future correction after the canonical freeze:

1. Preserve a sole-owner reservation for the exact successful OS-created child before polling it. At observed completion, save the owned PID/exit code, consume that reservation exactly once, release the mapped entry, and only then discard pid. The existing metadata chooser already demonstrates this pattern for the pinned Windows engine. Do not apply that Windows-map assumption blindly to arbitrary engines/platforms or fake test PIDs.
2. Clear the reservation before the one release call. An already-exited mapped child may yield FAILED while still being released; never retry OS.kill, since a later call can take the generic raw-PID path. Keep the saved result/status/adoption behavior unchanged.
3. Keep cancel cooperative while the preparer is live, then use the same terminal release path. Any forced-shutdown change must explicitly own/cancel/wait for the child tree; it is separate from merely releasing a completed handle.
