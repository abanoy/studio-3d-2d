# Native Source oracle proposal — research only

Researched 2026-11-13. No local viewer, model runtime, GUI, GPU, installer, download, Steam write, registry write, or production edit was performed. Only official Valve-hosted documentation and ValveSoftware source were used for technical conclusions. Search results from third-party forks, tutorials, and leaked-source repositories were not treated as Valve support evidence.

**Recommendation:** keep a matching, installed Source HLMV as a conditional small native oracle, but do not yet represent an unattended HLMV capture route as verified. Start with compatibility and control discovery on one native model from each case under the root's future GPU lease. The public official SDK source does establish useful native control semantics; it does not establish compatibility of an arbitrary installed HLMV with these MDL49 files.

## What primary sources establish

| Area | Primary evidence | Consequence and limit |
|---|---|---|
| SDK model version | Valve's Source SDK 2013 header declares `STUDIO_VERSION 48`. [studio.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/public/studio.h), around line 64 | This source is not proof of MDL49 reader compatibility. Do not lower the native file's version byte, recompile it, or substitute a converted GLB to make an oracle pass. |
| Official HLMV implementation | The browsed current official [src/utils tree](https://github.com/ValveSoftware/source-sdk-2013/tree/master/src/utils) does not contain HLMV. | No current HLMV command parser, screenshot implementation, or registry behavior was verified from that tree. This is an observation of this tree, not a claim that Valve has never released other viewer source. |
| Skins and posing controls | The official `CMDLPanel` header exposes `SetMDL`, `SetLOD`, `SetSequence`, `SetPoseParameters`, `SetPoseParameterByName`, `SetSkin`, and model angles/position. [mdlpanel.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/public/matsys_controls/mdlpanel.h), lines 51–81 | These are C++ panel APIs. They support a source-code inference about native panel capability, not a promise of matching HLMV GUI or command-line flags. Its `SetupFlexWeights` default is empty and virtual; this generic panel is not a complete ready-made flex viewer. |
| Low-level model state and custom bone matrices | Official `CMDL` stores skin, packed body state, sequence, LOD, time, and flex-control state. It offers automatic bone setup or drawing with caller-provided bone-to-world matrices. [mdlutils.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/public/tier3/mdlutils.h), lines 35–73 | A custom native harness is possible in principle, with native rendering libraries and matching ABI. It would be a separate implementation/build task. These declarations do not provide a standalone HLMV automation API or prove a match to an installed MDL49 branch. |
| Independent bodygroup selection | Valve's `SetBodygroup` updates one body's field using that body's `base` and `nummodels`; `GetBodygroup` reverses it. [animation.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/shared/animation.cpp), lines 799–831 | Native body values are packed fields, not the textual three-digit tuple used by the experimental HAS request. Enumerate native group indices/names/part indices; never pass `"010"` as a guessed packed integer. |
| Native entity controls | Valve's server animation code exposes skin, bodygroups, sequence, cycle, pose parameters, and playback controls and implements bodygroup getters/setters. [baseanimating.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/server/baseanimating.cpp), lines 246–286 and 2123–2163 | These are SDK game/entity interfaces, not demonstrated HLMV commands. Pose parameters and animation sequences must not be reported as arbitrary editable bone rotations. |
| Flex controller semantics | Valve's `SetFlexWeight` uses the controller's native minimum/maximum and clamps normalized state. `FindFlexController` returns controller zero after a failed name search. [baseflex.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/server/baseflex.cpp), lines 166–214 | Enumerate exact controller names/indices/ranges first; do not trust a nonnegative lookup result as proof the requested name exists. A flex descriptor named Tools is not, by itself, proof of an accessible controller named Tools. |
| Flex rules | Valve's client flex code runs the studio header's flex rules to obtain final descriptor weights. [c_baseflex.cpp](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/game/client/c_baseflex.cpp), lines 289–312 | A native controller value is not generally identical to a raw descriptor/GLB morph weight. The Tools 0/0.5/1 comparison needs the controller-to-descriptor rule/range correspondence, or must explicitly remain a raw descriptor reference. |
| Native pixels | Official material context declares render targets, viewport, light setup, and `ReadPixels`. [imaterialsystem.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/public/materialsystem/imaterialsystem.h), lines 1086–1152 | A native C++ renderer could produce its own pixel readback; this is source-level feasibility, not evidence that installed HLMV has a supported screenshot CLI. It still requires real rendering/GPU execution. |
| SFM alternative | Valve's official FAQ describes SFM as native to Source, using game assets and hardware rendering; it discusses loading custom TF items/mod assets, including recompilation. [SFM FAQ](https://www.sourcefilmmaker.com/faq/) | SFM is a plausible alternative native host when the matching viewer fails. The FAQ does not guarantee these exact unchanged MDL49 inputs, arbitrary branch interchange, a headless mode, or scripted captures. Recompilation would invalidate an unchanged-input oracle. |

The format header also distinguishes flex descriptors, controllers, UI remaps and rule tables, and describes native pose parameters separately. Those distinctions support the limits above; they do not supply the missing exact-file controller inventory. [Valve studio.h](https://raw.githubusercontent.com/ValveSoftware/source-sdk-2013/master/src/public/studio.h), around lines 837–919 and 2093–2102.

## HLMV documentation not verified here

The Valve Developer Community pages for [Half-Life Model Viewer (Source)](https://developer.valvesoftware.com/wiki/Half-Life_Model_Viewer_(Source)), [Half-Life Model Viewer](https://developer.valvesoftware.com/wiki/Half-Life_Model_Viewer), [Model Viewer](https://developer.valvesoftware.com/wiki/Model_Viewer), and [MDL](https://developer.valvesoftware.com/wiki/MDL) returned HTTP 403. Public wiki raw/API views were also unavailable. They are follow-up documentation targets, not citations supporting particular viewer behavior in this research.

Consequently the following remain **unverified**, rather than positively unsupported in every build: HLMV `-game`/model-path argument syntax; any skin/bodygroup/flex/pose CLI flags; `.mvscript` grammar and whether it is implemented; fixed camera/numeric flex automation; batch exit; screenshot/TGA export; unattended screenshots without modal UI; offline Steam behavior; and whether viewer preferences touch the current user's registry. No guessed flags or third-party screenshot scripts are proposed as executable commands.

## Future execution gates and receipts

1. Read-only inventory the installed candidate HLMV executable, dependent native runtime/shader DLLs, and matching branch/game data. Hash/stamp their files; keep the two native MDL hashes and their VVD/VTX companions fixed. Do not download a third-party viewer or build the SDK as part of this research scope.
2. Establish a disposable owned mount retaining original `models/` and `materials/` layout, only the approved exact dependency closure, and explicit native material search paths. Do not write into Steam. Keep missing Nitori `hairbump` classified as a native missing-resource limit; do not invent it or borrow an unrelated resource silently.
3. Before any launch, inspect how that exact installed build chooses game roots, writes logs/screenshots/preferences, and initializes Steam. Establish owned output/profile behavior and the same independently observed private desktop/closed-job policy used for other native tools. A private desktop does not itself isolate registry/preferences. Stop if the host cannot meet that scope.
4. Under the root's separate GPU lease, first open one unchanged model per case with its native dependencies and record successful version/model load, exact native selectors and material resolution. Do not proceed to a screenshot matrix after an error-model, missing entire component, or incompatible-version result.
5. Fix camera, resolution, background, light, LOD, sequence/cycle and playback state across variants. Record all native selections and capture route beside each image. Native-versus-PBR color pixels are not expected to be identical because shader/lighting behavior differs; compare component presence, material identity, shape and the specifically tested deformation instead.
6. Preserve all failures, native warnings and input/output receipts. Hash originals/runtime before and after. If no supported unattended capture route can be established, an explicitly observed native-viewer session is useful evidence but must be labeled manual/native visual review, not automated native numerical equivalence.

No native fidelity result or actual MDL49 viewer support result is asserted by this proposal.
